# v0.8 个人状态与来源提交记录

## 用户可见修复

“标记完成”只表示个人工作流完成，不代表向学校提交。学校修改标题、日期或提交观察后，已确认的个人状态不再被自动覆盖。任务详情分别展示“个人状态”和每条“来源提交记录”；多来源不猜一个综合提交结论，unknown显示“未能确认”，无记录不代表已提交。远程看板不展示来源细节。

## 数据与兼容

- 复用现有status操作、权限、CSRF、业务版本与幂等；没有新状态写接口或新表。仅明确操作写personal_status对象：state/origin/actor/updated_at。API禁止直接传入personal_status修改。
- 个人决定存在时，item.status保留该工作流状态供旧接口、提醒和排程兼容；来源submission_status仍独立保存在原有evidence/source_records，不伪造学校提交。通知中的“完成”同样记录明确个人决定。
- 明确重新打开也保留，即使学校已提交，仍可作为修改/跟进任务。代价是这些明确管理的事项不再因学校后来提交自动关闭；UI会分别展示两个事实。
- 新建事项以personal_status:null明确表示尚无个人决定；旧记录字段缺失才进入历史完成补标记，避免把新来源自身的completed错当历史个人决定。
- 未有个人决定的来源事项继续沿用原有自动提交/unknown逻辑，不改变未知观察不能抹掉已知提交的处理。

## 旧数据迁移

已有completed且无个人标记的事项保守增加origin=legacy_completed，UI显示“历史完成（来源未区分）”，不臆测是谁点击、不创造时间或提交证据。代价是来源自身历史完成也保持关闭，需明确操作才能重新打开。已有submitted及其他非completed旧记录补personal_status:null，不推断为个人完成；这样旧活跃事项后来首次收到来源completed也不会被误判为历史个人完成。

迁移在保留写锁后备份到data_dir/backups/personal-status-*.sqlite3；备份失败不提交元数据。仅补JSON元数据，原ID、业务版本、更新时间、安排、日历映射、历史审计与旧幂等回执不改变；重复/并发启动只迁移一次。正常来源同步也保护未补标记的历史completed。

源码回滚不自动回滚用户数据库；迁移备份单独保留，恢复数据应先核对备份之后的新操作，避免抹掉后续历史。本轮仅在虚构临时数据库运行迁移与恢复验收，未重启真实账号服务。
