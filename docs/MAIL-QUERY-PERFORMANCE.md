# v0.7 邮件核对筛选查询优化

## 修改

原 pending/ignored 条件对每封邮件执行关联 EXISTS，反复解析全部事项核对状态。现在用不相关的 IN 子查询构建匹配邮件键集合，每条 count/page SQL 计算一次，再匹配邮件。

保留当前SQLite、JSON关联、表/索引、ID、业务版本、历史、权限/CSRF/幂等和写接口。没有更换数据库、写真实数据库或重启账号服务。全部读取仍在原有单个事务快照中进行。

## 语义与成本验收

- 新增6个测试用例；其中旧版3个成本断言失败，语义用例原本通过。新实现6个全部通过。
- 240封邮件、100事项：pending/ignored筛选 count+page 的状态函数评估总次数上限200；旧相关查询超过预算。
- 1000封邮件、200事项：固定500000条SQL VM指令预算内完成，不以机器墙钟速度作回归门槛。
- 组合关键词/账号/本地日期/分页与Python权威关联枚举一致；重复邮件键不重复计数，孤立关联不产生假邮件，混合来源不被当作待核对。
- 同封邮件可同时含pending/ignored候选；确认和恢复后下一次读取立即反映状态，不使用会过期的持久缓存。所有测试使用临时虚构数据。

## 基准比较

使用与v0.6相同 scripts/benchmark-board.py，虚构1000/10000封邮件与1000事项（100待核对）。直接Core调用，不代表HTTP/UI或账号服务内存。每条连接SQL预算5秒；5个暖样本p95为最近秩最大值，不作为SLA。旧值超限只表示>5秒，不把删失时间当真实完整耗时，也不声称精确加速倍数。
